Lección 1.1

¿Qué es Claude Code y dónde corre?

Claude Code es un asistente agéntico. No solo responde texto: usa herramientas para leer tu código, editar archivos, ejecutar comandos y buscar en la web. La documentación lo describe como la capa que rodea al modelo, provee las herramientas y administra el contexto que el modelo ve. A esa capa se le llama harness agéntico.

Aunque brilla programando, sirve para cualquier cosa que puedas hacer desde la línea de comandos: escribir documentación, correr builds, investigar un tema o buscar archivos.

Dónde puedes usarlo

El loop agéntico es idéntico en todas las superficies. Lo que cambia es dónde se ejecuta el código y cómo interactúas.

La idea claveEn un chat tú eres el puente: copias contexto, pegas respuestas y corres comandos. Con un agente, él recorre ese puente: busca contexto, edita, corre los tests y lee los errores por su cuenta. Tu trabajo pasa a ser dirigir y verificar.

Lección 1.3
El loop agéntico y las herramientas

  
Cuando le das una tarea, Claude trabaja en tres fases que se mezclan: reunir contexto, actuar y verificar. Se repiten hasta cumplir el objetivo. Una pregunta puede necesitar solo contexto; un bug recorre las tres fases varias veces. Tú también eres parte del loop: puedes interrumpir en cualquier momento.

Lección 1.7
Interrumpir y redirigir

  
No necesitas prompts perfectos. Claude Code es conversacional: empiezas con lo que quieres y vas corrigiendo. Lo importante es corregir temprano.

  

  

    
Quieres…Haz esto

    
      
Detenerlo yaEsc. Cancela la herramienta en curso, conserva el trabajo hecho y espera tu instrucción.

      
Corregir sin detenerloEscribe y presiona Enter. El mensaje queda en cola; si Claude está corriendo herramientas, lo lee apenas terminen, dentro del mismo turno.

      
Enviar ya lo encoladoCtrl+Enter

Hacer una pregunta al margen/btw ¿qué versión de Node usa este repo?. La respuesta no entra al historial, así no crece el contexto.

Lección 1.9
Verificación: la regla de oro

  
Claude se detiene cuando el trabajo parece terminado. Sin un chequeo que pueda correr, "parece terminado" es la única señal, y tú te conviertes en el loop de verificación. Con algo que devuelva pasa/falla (tests, código de salida de un build, un linter, un script que compara contra un fixture, una captura de pantalla), el loop se cierra solo.

  

    
EstrategiaAntesDespués

    
      
Criterios verificables"implementa una función que valide emails""escribe validateEmail. Casos: user@example.com es true, invalid es false, user@.com es false. Corre los tests al terminar"

      
UI visual"mejora el dashboard""[captura] implementa este diseño, toma una captura del resultado, compáralas, lista diferencias y corrígelas"

      
Causa raíz"el build está fallando""el build falla con este error: [error]. Arréglalo y verifica que el build pase. Ataca la causa raíz, no suprimas el error"

    
  

  
Cuatro niveles de exigencia

  
    
    
  • En un prompt: pide que corra el chequeo e itere en el mismo mensaje.
    • 
    
  • En toda la sesión: fíjalo como condición con /goal; un evaluador revisa después de cada turno (nivel Experto).
    • 
    
  • Como compuerta determinista: un hook Stop que corre tu chequeo y no deja terminar el turno hasta que pase (nivel Avanzado).
    • 
    
  • Con segunda opinión: un subagente revisor con contexto limpio intenta refutar el resultado, así quien hizo el trabajo no se califica a sí mismo.
    • 
  

  
Pide evidenciaPide que muestre la salida de los tests, el comando que corrió y lo que devolvió, o una captura. Revisar evidencia es más rápido que volver a verificar tú, y funciona para sesiones que no estabas mirando. Después de que su chequeo pase, /verify confirma el cambio en la app corriendo.

Lección 2.1
Modos de permiso

  
El modo define qué hace Claude sin preguntarte. Desde la versión 2.1.283, las sesiones interactivas de terminal y VS Code parten en modo auto (antes solo en planes Pro, Max y Team). Las corridas con claude -p y el Agent SDK parten en modo Manual. Cambia de modo con Shift+Tab: enfoca el widget y pruébalo.

  
Ciclo de modos

    

      

      

      
AcciónComportamiento

    

  

  
Cómo funciona el modo auto

  
Un modelo clasificador separado revisa las acciones antes de ejecutarlas y bloquea lo que escala más allá de tu pedido, apunta a infraestructura desconocida o parece motivado por contenido hostil. Lecturas y ediciones dentro del directorio de trabajo se aprueban sin pasar por el clasificador.

  

    
Bloqueado por defectocurl | bash, deploys y migraciones a producción, force push, git reset --hard, terraform destroy, mergear PRs sin aprobar, imprimir credenciales en el transcript.

    
Permitido por defectoOperaciones locales en el directorio de trabajo, instalar dependencias declaradas en lockfiles, requests HTTP de solo lectura, push a ramas del repo que no sean de deploy.

  

  
    
    
  • Si dices "no hagas push" en la conversación, se trata como un bloqueo hasta que lo levantes. Pero puede perderse al compactar: para una garantía real, usa una regla deny.
    • 
    
  • Tras 3 bloqueos seguidos o 20 en total, auto mode se pausa y vuelven los prompts. Las acciones bloqueadas aparecen en /permissions bajo "Recently denied"; con r reintentas con aprobación manual.
    • 
    
  • dontAsk no está en el ciclo: se activa con --permission-mode dontAsk y deniega todo lo que pediría permiso. Ideal para CI.
    • 
    
  • auto y bypassPermissions no se aceptan como defaultMode en settings del proyecto; ponlos en ~/.claude/settings.json.
    • 
  

  
bypassPermissionsSolo en contenedores o VMs aislados, idealmente sin internet. No protege contra prompt injection. En Linux y macOS, Claude Code se niega a arrancar como root en este modo salvo que detecte un sandbox reconocido. Las reglas deny siguen aplicando.

  





  
Lección 2.2
Reglas allow / ask / deny

  
Encima del modo defines reglas finas con la sintaxis Herramienta(especificador). Se evalúan en orden fijo: deny, luego ask, luego allow. Gana la primera coincidencia en ese orden; la especificidad no cambia el orden. deny bloquea en todos los modos, incluido bypass.

  

  
Probador de reglas Bashsimplificado según la documentación

    

      

        
        

        
        
        
        

      

      

        
Un * coincide con cualquier texto, espacios incluidos. Un ␣* final también coincide con el comando pelado (Bash(ls *) coincide con ls, no con lsof). En comandos compuestos con &&, ||, ; o |, cada subcomando debe coincidir con un allow; un deny o ask aplica si coincide con cualquiera.

      

    

  

  
Sintaxis por herramienta

  

    
ReglaSignificado

    
      
Bash(npm run *)Cualquier script de npm. Pon el * después del subcomando, no antes.

      
Read(./.env)Ruta relativa al directorio actual

      
Edit(/src/**/*.ts)Ruta relativa al origen de la configuración (en settings del proyecto: la raíz del proyecto)

      
Read(~/.ssh/**)Desde tu home

      
Read(//etc/**)Ruta absoluta desde la raíz del sistema

      
WebFetch(domain:docs.stripe.com)Solo ese dominio; *.example.com cubre subdominios

      
mcp__github__*Todas las herramientas del servidor MCP github

      
Agent(Explore)Un subagente específico (útil en deny)

    
  

  
.claude/settings.json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(pnpm run *)", "Bash(git diff *)", "Bash(git log *)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}

  
Límite de las reglas BashUna regla coincide con el texto del comando tal como Claude lo escribe. Bash(curl *) no detiene /usr/bin/curl … ni sh -c 'curl …'. Para una barrera que no dependa del texto, usa el sandbox (Avanzado) o un hook PreToolUse.

  
/permissions abre un diálogo para ver reglas por scope, agregarlas o quitarlas. La skill incluida /fewer-permission-prompts revisa tus transcripts y propone una allowlist priorizada de comandos de solo lectura.

Lección 2.3
CLAUDE.md: qué poner y qué no

  
CLAUDE.md es un Markdown que Claude lee al inicio de cada sesión. Escribe ahí lo que, de otro modo, tendrías que volver a explicar. /init genera uno inicial; si ya existe, sugiere mejoras en vez de sobrescribirlo.

  

    
 Incluir Excluir

    
      
Comandos Bash que Claude no puede adivinarLo que Claude deduce leyendo el código

      
Reglas de estilo que difieren de lo estándarConvenciones del lenguaje que Claude ya conoce

      
Cómo correr tests y qué runner preferirDocumentación de API detallada (enlázala)

      
Etiqueta del repo: ramas, PRsInformación que cambia seguido

      
Decisiones de arquitectura propias del proyectoExplicaciones largas o tutoriales

      
Peculiaridades del entorno (variables requeridas)Descripciones archivo por archivo

      
Trampas y comportamientos no obviosObviedades como "escribe código limpio"

    
  

  
Constructor de CLAUDE.md

    

      

        
        

        
        
        
        
      

      

    

  

  
    
    
  • Tamaño: apunta a menos de 200 líneas por archivo. Archivos largos consumen contexto y bajan la adherencia.
    • 
    
  • Concreto y verificable: "usa indentación de 2 espacios" en vez de "formatea bien"; "corre npm test antes de commitear" en vez de "prueba tus cambios".
    • 
    
  • Para cada línea pregúntate: "¿quitarla haría que Claude se equivoque?". Si no, bórrala.
    • 
    
  • Énfasis: si ignora una instrucción, marca solo esa con "IMPORTANT". Si enfatizas muchas, ninguna destaca.
    • 
    
  • Auditoría: /doctor prompt-audit busca instrucciones obsoletas, referencias rotas y contradicciones, y propone ediciones.
    • 
    
  • Comentarios HTML (<!-- nota -->) se eliminan antes de inyectarse: notas para humanos que no cuestan tokens.
    • 
  

  
Cuándo agregar algoCuando Claude comete el mismo error por segunda vez, cuando un code review detecta algo que Claude debió saber, o cuando escribes la misma corrección que la sesión anterior. Trata CLAUDE.md como código: versiónalo, revísalo y pódalo.

Lección 2.8
Tokens y prompt caching

  
Claude no lee palabras: lee tokens, trozos de texto que pueden ser una palabra corta, parte de una palabra larga o un símbolo. Todo se mide en tokens: lo que entra (tu prompt, los archivos, la conversación) y lo que sale (la respuesta y el razonamiento). Y todo se cobra en tokens, o se descuenta de los límites de tu plan.

  
Hay un detalle que cambia cómo conviene trabajar: el modelo no recuerda nada entre un mensaje y otro. En cada turno, Claude Code vuelve a enviar la conversación completa: instrucciones de sistema, herramientas, CLAUDE.md, cada archivo leído y cada respuesta anterior. Una sesión de 100k tokens envía esos 100k tokens otra vez con cada mensaje nuevo.

  
En simple
    
Sin caché, cada mensaje pagaría de nuevo toda la conversación. El prompt caching guarda el comienzo de lo que ya enviaste; mientras ese comienzo siga idéntico y el caché no haya expirado, se cobra a una fracción del precio. Claude Code lo usa solo, sin configurar nada. Tu trabajo es no romperlo sin darte cuenta.

Lección 2.9
Hábitos que ahorran tokens

  
El gasto innecesario casi nunca viene de un prompt caro. Viene de hábitos: conversaciones que se arrastran entre tareas, salidas de comandos gigantes, capturas a resolución completa, instrucciones que se cargan en cada mensaje aunque no se usen. Esta es la lista de la documentación oficial, ordenada por dónde se va el consumo.


  

    
Qué consumeCómo bajarlo

    
      
Una conversación larga que ya no sirve/clear al cambiar de tarea. Si quieres volver después, nómbrala con /rename y retómala con /resume. Todo lo que queda en el contexto se reenvía en cada mensaje.

      
Salida y razonamientoSonnet para la mayoría de las tareas; Opus para arquitectura y razonamiento de varios pasos. Baja el effort con /effort en tareas simples: el razonamiento se cobra como salida.

      
Salidas de comandos enormesFiltra antes de que lleguen a Claude: un hook PreToolUse puede dejar solo las últimas 100 líneas de npm test. O delega tests, logs y búsquedas a un subagente: el ruido queda en su contexto y vuelve solo el resumen.

      
Un CLAUDE.md largoSe envía completo en cada mensaje. Mantenlo bajo 200 líneas y mueve los procedimientos largos a skills, que cargan solo cuando se usan.

      
Servidores MCPSus herramientas se cargan bajo demanda por defecto. Aun así, prefiere las CLI cuando existen (gh, aws, gcloud) y desactiva con /mcp los servidores que no usas.

      
Buscar a ciegas en el códigoUn plugin de code intelligence para lenguajes tipados deja navegar por símbolos en vez de hacer grep y leer archivo por archivo.

      
Imágenes y PDFUna imagen cuesta (ancho ÷ 28) × (alto ÷ 28) tokens, redondeando hacia arriba: una captura de 1000×1000 son unos 1.300 tokens. Recorta la captura a lo relevante. Un PDF cuesta entre 1.500 y 3.000 tokens de texto por página, más la imagen de cada página.

      
Subagentes y agent teamsCada subagente hace sus propias peticiones, que cuentan en los mismos límites que tu sesión. Los agent teams gastan bastante más que una sesión sola (un teammate en plan mode, unas 7 veces más). Úsalos para investigación, revisión o features nuevas; usa Sonnet en los teammates y ciérralos al terminar.

      
Prompts vagos"Agrega validación al login en auth.ts" gasta mucho menos que "mejora el código", porque Claude no tiene que explorar para adivinar qué quieres. Planifica con plan mode antes de implementar y corrige temprano con Esc.

      
Procesos de fondoLas sugerencias de prompt y la compactación en inactividad (idleCompaction) consumen poco, pero se pueden desactivar.

    
  


  
/clear o /compact

  

    
/clearNo cuesta nada. Úsalo al cambiar de tarea: empiezas con un contexto limpio y pequeño.

    
/compactEs una petición grande: lee toda la conversación para resumirla. Úsalo cuando necesitas seguir en la misma tarea y la conversación ya está larga, mejor con caché activo.

    
/rewindPara descartar un camino que no funcionó. Vuelve a un punto que ya está en caché, sin resumir nada.

  


  
Suscripción o API key

  
    
    
  • Con suscripción no pagas por token: tu uso se descuenta de una ventana de 5 horas y de una semanal, compartidas con claude.ai. /usage muestra ambas barras y cuándo se reinician. Al llegar al tope verás You've hit your session limit o You've hit your weekly limit.
    • 
    
  • Con API key pagas cada token según la tabla de la lección anterior. /usage estima el costo a precio de lista.
    • 
    
  • En ambos casos, los hábitos de esta lección rinden lo mismo: menos tokens enviados significa más trabajo antes del límite o una factura menor.
    •

Lección 2.13

El advisor es una función experimental que combina dos modelos en la misma sesión. El principal hace todo el trabajo: lee archivos, edita y corre comandos. Un subagente es un trabajador con su propia ventana de contexto, su propio system prompt y su propio set de herramientas. Puede leer decenas de archivos; a tu conversación solo vuelve un resumen. Como el contexto es tu recurso más escaso, esto es lo que los hace valiosos.

    •

Lección 3.9

Lección 3.11
Worktrees y sesiones paralelas

  
Un git worktree es un directorio de trabajo separado, con su propia rama, que comparte historial y remoto con tu checkout principal. Con cada sesión en su worktree, las ediciones de una nunca tocan los archivos de otra.

  

  
bash
# crea .claude/worktrees/feature-auth en la rama worktree-feature-auth
claude --worktree feature-auth

# en otra terminal, otra sesión aislada
claude -w bugfix-123

# worktree a partir de un pull request (comillas por el #)
claude --worktree "#1234"

  
    
    
  • Agrega .claude/worktrees/ a tu .gitignore.
    • 
    
  • Archivos ignorados: un worktree es un checkout limpio, sin tu .env. Crea .worktreeinclude (sintaxis de .gitignore) para copiarlos automáticamente.
    • 
    
  • Rama base: por defecto parte de la rama default del remoto. Con "worktree": {"baseRef": "head"} en settings parte de tu HEAD local.
    • 
    
  • Limpieza: al salir, si el worktree está limpio se borra; si tiene cambios o commits, Claude te pregunta si conservarlo.
    • 
    
  • También puedes pedir "trabaja en un worktree" y Claude lo crea. Los subagentes con isolation: worktree usan uno temporal.
    • 
  

  
Patrón escritor / revisor

  
Un contexto nuevo revisa mejor porque no está sesgado hacia código que acaba de escribir. Sesión A: "implementa un rate limiter para la API". Sesión B: "revisa el rate limiter en @src/middleware/rateLimiter.ts buscando casos borde, condiciones de carrera y consistencia con nuestros middlewares". Luego pasas el feedback a A. Lo mismo funciona con tests: una sesión los escribe y otra escribe el código que los pasa.

Lección 4.6
Dynamic workflows

  
Un workflow dinámico es un script JavaScript que Claude escribe y un runtime ejecuta en segundo plano mientras tu sesión sigue libre. La diferencia con los subagentes es quién tiene el plan: con subagentes, Claude decide turno a turno; en un workflow, el script tiene el loop, las ramas y los resultados intermedios, así tu contexto solo recibe la respuesta final.

  
Fan-out / fan-in con verificación

    
Tarea: "audita la seguridad del módulo de pagos antes del release". Toca orquestar para ver cómo el script reparte el trabajo, junta los resultados y los verifica antes de entregártelos. La barra de cada caja es el contexto que usa.

  

  
Cómo lanzar uno

  
    
    
  • Incluye la palabra ultracode o pide "usa un workflow" en tu prompt.
    • 
    
  • /effort ultracode deja que Claude planifique un workflow para cada tarea sustancial de la sesión (más tokens y más tiempo por pedido).
    • 
    
  • /deep-research <pregunta> es el workflow incluido: busca en la web desde varios ángulos, contrasta fuentes y entrega un reporte citado.
    • 
    
  • /workflows muestra el progreso por fase y agente; con s guardas el script como comando reutilizable en .claude/workflows/.
    • 
  

  
.claude/workflows/audit-routes.js
export const meta = {
  name: 'audit-routes',
  description: 'Audita cada route handler buscando auth faltante',
}

const found = await agent('Lista cada archivo .ts bajo src/routes/.', {
  schema: { type: 'object', required: ['files'],
            properties: { files: { type: 'array', items: { type: 'string' } } } },
})

const audits = await pipeline(found.files, file =>
  agent(`Audita ${file} buscando chequeos de autenticación faltantes.`, { label: file }),
)

return audits.filter(Boolean)

  
agent() lanza un subagente, pipeline() uno por elemento de una lista y parallel() varios a la vez. Límites: 16 agentes concurrentes por defecto y 1.000 por corrida. Un workflow pausado se reanuda; uno que pasa los 25 agentes o 1,5 M de tokens proyectados muestra la advertencia "Large workflow".

  
Prompts que encajan"usa un workflow para auditar cada handler en src/routes/ y verifica adversarialmente cada hallazgo antes de reportarlo" · "usa un workflow para migrar cada componente de src/components/ a TypeScript, cada archivo en su copia aislada" · "usa un workflow para correr tsc y seguir arreglando hasta que pase o dos rondas seguidas no avancen".

Con -p Claude Code corre sin interfaz: recibe un prompt, trabaja y devuelve el resultado. Es la puerta para pipelines, pre-commit hooks y fan-outs. Sale con código 0 si tuvo éxito.

# modo bare: no carga hooks, skills, MCP, CLAUDE.md ni auto memory (recomendado en CI)
claude --bare -p "resume README.md" --allowedTools "Read"

# salida estructurada validada contra un schema → campo structured_output
claude -p "extrae los nombres de funciones de auth.py" --output-format json \
  --json-schema '{"type":"object","properties":{"functions":{"type":"array","items":{"type":"string"}}},"required":["functions"]}' \
  | jq '.structured_output'

claude -p "corre los tests y arregla los que fallen" \
  --allowedTools "Read,Edit,Bash(pnpm test *)" \
  --permission-mode dontAsk --max-turns 20 --max-budget-usd 5.00

# commit con herramientas acotadas
claude -p "revisa mis cambios staged y crea un commit apropiado" \
  --allowedTools "Bash(git diff *),Bash(git log *),Bash(git status *),Bash(git commit *)"

# continuar una conversación concreta
sid=$(claude -p "inicia una revisión" --output-format json | jq -r '.session_id')
claude -p "continúa esa revisión" --resume "$sid"

GitHub Actions y Code Review

  
La acción anthropics/claude-code-action@v1 corre Claude Code dentro de tus workflows. Sin prompt trabaja en modo interactivo: responde a @claude en issues y PRs. Con prompt trabaja en modo automatización ante cualquier evento, incluido cron.

  

  
    
    
  • Setup rápido: /install-github-app dentro de Claude Code instala la app, guarda el secreto y abre el PR con el workflow.
    • 
    
  • Secretos: ANTHROPIC_API_KEY (Claude Console) o CLAUDE_CODE_OAUTH_TOKEN generado con claude setup-token para usar tu suscripción.
    • 
  

  
.github/workflows/claude.yml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--max-turns 10 --model claude-sonnet-5"

    • 
    
  • Solo usuarios con permiso de escritura y actores humanos (salvo allowed_bots) pueden disparar corridas.
    •

Hooks
Código tuyo que se ejecuta automáticamente en momentos exactos del ciclo de vida de Claude Code. Es la única forma de convertir una regla en una garantía: formatear siempre, bloquear siempre, avisar siempre.

  

    

    




  
HOOKS · 1
Qué es un hook, en simple

  
En simpleUn hook es una regla del tipo "cuando pase X, ejecuta Y". Como un sensor de movimiento que prende la luz: no depende de que alguien se acuerde. Claude puede olvidar una instrucción de tu CLAUDE.md; un hook se ejecuta siempre, porque lo corre Claude Code, no el modelo.

  

    
CLAUDE.md dice…
"Corre prettier después de editar"
Sugerencia. El modelo decide si lo hace. Puede olvidarlo tras compactar.

    
vs

    
Un hook PostToolUse…
jq -r '.tool_input.file_path' | xargs npx prettier --write
Garantía. Corre después de cada Edit o Write, sin excepción.

  

  
Qué puedes hacer con hooks

  

    
BloquearImpedir comandos peligrosos o ediciones a .env, incluso en modo bypass.

    
AutomatizarFormatear, correr linters o tests después de cada cambio.

    
Inyectar contextoAgregar la rama actual, el sprint o recordatorios al prompt o tras compactar.

    
NotificarAviso de escritorio o Slack cuando Claude espera tu respuesta.

    
AprobarResponder automáticamente prompts de permiso que siempre aceptas.

    
AuditarRegistrar cada comando o cambio de configuración para cumplimiento.

  

  
Cinco tipos de handlerUn hook puede ser un comando de shell (command, el más común), un POST a una URL (http), una llamada a una herramienta MCP (mcp_tool), una evaluación de un LLM (prompt) o un subagente con herramientas (agent, experimental).

Probador de matchers

    

      

        

      

    

  

  
Filtra también por argumentos con if

  
El matcher solo ve el nombre de la herramienta. Para filtrar por qué hace, agrega if al handler con sintaxis de reglas de permiso. Así el proceso ni siquiera se lanza si no coincide:

  
.claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git push *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/check-branch.sh"
          }
        ]
      }
    ]
  }
}

Salida: exit codes y JSON

  
Tu hook le responde a Claude Code de dos formas. Elige una por hook:

  

    
Forma simple: exit code0 = sin objeción · 2 = bloquear (el motivo va a stderr) · otro = error no bloqueante, la acción sigue.

Campos JSON universales

  
CampoEfecto

systemMessageAviso que se muestra al usuario.

EventosCómo deciden

    
PreToolUse, PreModelSwitchhookSpecificOutput.permissionDecision: allow / deny / ask (y defer en -p) + permissionDecisionReason

SKILLS · 1
Qué es una skill, en simple

  
En simpleUna skill es una receta en una tarjeta. En la cocina hay un fichero con cientos de recetas, pero el chef solo ve los títulos. Cuando alguien pide "lasaña", saca esa tarjeta y la lee entera. Claude hace lo mismo: ve el nombre y la descripción de todas tus skills, y solo carga el contenido completo de la que necesita.

  
Técnicamente es una carpeta con un archivo SKILL.md: frontmatter YAML que dice cuándo usarla y un cuerpo en Markdown que dice cómo. Claude la carga sola cuando la descripción coincide con lo que pides, o la ejecutas tú con /nombre-de-la-skill.

  
Carga progresiva: por qué no gastan contexto

  
Tres capas de cargabarra = contexto que ocupa

    

      

        
1 · Listadosiempre en contexto
Nombre + descripción de cada skill (máx. 1.536 caracteres por skill). Así Claude sabe qué existe.

        
2 · Cuerpo de SKILL.mdsolo al invocarla
Las instrucciones completas entran cuando Claude o tú la invocan. Recomendado: menos de 500 líneas.

        
3 · Archivos de apoyobajo demanda
reference.md, examples.md, plantillas: Claude los lee solo si el SKILL.md lo dirige ahí. Los scripts se ejecutan sin cargarse al contexto.

Archivos de apoyo y context: fork

  

    

      
Organiza la carpeta

      
.claude/skills/pdf-forms/
├── SKILL.md          ← instrucciones (<500 líneas)
├── reference.md      ← detalle, se lee si hace falta
├── examples.md       ← ejemplos de entrada/salida
├── templates/
│   └── informe.md
└── scripts/
    └── fill_form.py  ← se ejecuta, no se carga

      
En el SKILL.md enlaza cada archivo diciendo cuándo leerlo: "Para campos de firma, lee reference.md".

    

    

      
Ejecutar en un subagente

      
Con context: fork la skill corre en un subagente aislado: lee mucho y te devuelve solo el resultado. agent elige el tipo (por defecto general-purpose; Explore para solo lectura). Con background: false esperas el resultado en el mismo turno.

      
SKILL.md
---
name: investigar
description: Investiga a fondo un tema del código
context: fork
agent: Explore
---
Investiga $ARGUMENTS a fondo:
1. Encuentra los archivos relevantes con Glob y Grep
2. Lee y analiza el código
3. Resume hallazgos con referencias archivo:línea

      
OjoEl subagente no ve tu conversación. Las instrucciones deben bastarse solas: una skill de "guías" sin tarea concreta no produce nada útil en fork.

SKILLS · 14
Un estándar abierto y portable

  
Las Agent Skills nacieron en Claude, pero el formato SKILL.md es un estándar abierto: la misma carpeta funciona en Claude Code, claude.ai, la API y en otros agentes y herramientas compatibles. En octubre de 2026 Anthropic donó el estándar a la Agentic AI Foundation, bajo la Linux Foundation.

  
    
    
  • Para que una skill sea portable, usa solo los campos estándar y pon la lógica en el cuerpo y en scripts.
    • 
    
  • Los campos propios de Claude Code (context, hooks, paths, model…) se ignoran o fallan fuera de él.
    • 
    
  • Distribuye skills a tu equipo commiteándolas en el repo o empaquetándolas en un plugin con un marketplace.
    •

SETTINGS · 1
Settings, en simple

  
En simplePiensa en capas de reglas, como en una casa: las reglas del edificio (organización) mandan sobre las de la familia (equipo), que mandan sobre tus preferencias (usuario). Y para una sola noche, puedes hacer una excepción (línea de comandos). Claude Code lee varias capas y, si dos dicen cosas distintas, gana la más alta.

  

    
settings.jsonComportamiento de Claude Code: modelo, permisos, hooks, sandbox, interfaz. Lo aplica el programa.

    
CLAUDE.mdInstrucciones para el modelo: convenciones, comandos de build. Es contexto, no configuración.

    
Variables de entornoAlgunas tienen pareja en settings (ANTHROPIC_MODEL ↔ model); quién gana se decide por cada par.

  

  
Los archivos son JSON estricto: un comentario // o una coma final es error de sintaxis. Agrega "$schema": "https://json.schemastore.org/claude-code-settings.json" y tu editor te dará autocompletado y validación.






  
SETTINGS · 2
Los archivos y a quién afectan

  
Tienes tres proyectos en tu máquina, un compañero con su copia de acme-app y una sesión en la nube sobre acme-app. Toca un archivo para ver hasta dónde llega:

  
Alcance de cada archivo

    

      

      

      

    

  

  
ScopeArchivoAfecta aÚsalo para

    
Usuario~/.claude/settings.jsonTú, en todos tus proyectosTema, modelo por defecto, tus reglas personales

    
Proyecto compartido.claude/settings.jsonTodos en el repo (commitéalo)Permisos, hooks, plugins y env del equipo

    
Proyecto local.claude/settings.local.jsonTú, solo en este proyectoExcepciones personales; pruebas antes de compartir

    
Managedmanaged-settings.json, MDM, consola de claude.aiToda la organizaciónPolíticas de seguridad y cumplimiento

  

  
    
    
  • Instalar Claude Code no crea ningún archivo. Se crean cuando cambias algo en /config (usuario) o eliges "Yes, and don't ask again" en un prompt (local).
    • 
    
  • Claude Code agrega settings.local.json a tus exclusiones globales de git la primera vez que lo escribe. Si lo creas a mano, agrégalo tú a .gitignore.
    • 
    
  • Hay un quinto archivo, ~/.claude.json, que Claude Code mantiene solo: cuenta, servidores MCP de scope local/usuario, estado por proyecto. No necesitas editarlo.
    • 
    
  • En Windows, ~/.claude es %USERPROFILE%\.claude. Con CLAUDE_CONFIG_DIR lo mueves a otra ruta.

SETTINGS · 4
Cuatro formas de cambiar un setting

  

  
¿Cuándo hace efecto?

  
Claude Code vigila los archivos y recarga la mayoría de los cambios en la sesión en curso, incluidos permissions, hooks y apiKeyHelper. Cada cambio dispara el hook ConfigChange. Excepciones que se leen solo al arrancar: model (usa /model), effortLevel y modelSettings (usa /effort).
