Nivel 01 · Básico

Lo que Git guarda

Instala Git, haz tus primeros commits y entiende qué guarda de verdad: fotos completas del proyecto, enlazadas una con otra. Con esa idea, todo lo demás tiene sentido.

Lección 1.1

¿Qué problema resuelve Git?

Si alguna vez tuviste informe_final.docx, informe_final_v2.docx e informe_final_DEFINITIVO.docx, ya conoces el problema: guardar versiones a mano es desordenado, no dice qué cambió entre una y otra, y no sirve cuando dos personas trabajan en lo mismo.

Git es un sistema de control de versiones: guarda la historia de tu proyecto como una serie de fotos, cada una con quién la tomó, cuándo y por qué. Puedes volver a cualquier foto, comparar dos, y trabajar en paralelo con otras personas sin pisarse.

En simple

Git es una máquina del tiempo para una carpeta. Cada vez que guardas un punto (un commit), puedes volver a él cuando quieras, y ver exactamente qué cambió desde el anterior.

Git no es GitHub

Git es un programa que corre en tu computador y funciona sin internet. GitHub, GitLab y Bitbucket son servicios donde subes una copia de tu repositorio para compartirla, revisar cambios con tu equipo y automatizar pruebas. Puedes usar Git toda la vida sin GitHub; al revés, no.

DistribuidoCada copia del repositorio tiene la historia completa. Si el servidor desaparece, cualquier clon sirve para recuperarlo.
RápidoCasi todo ocurre en tu disco: ver el historial, cambiar de rama o comparar versiones tarda milisegundos.
SeguroCada versión se identifica por un hash de su contenido: si algo se corrompe o se altera, Git lo nota.

Lección 1.3
Tu primer repositorio

  
Hay dos formas de tener un repositorio: crearlo en una carpeta que ya tienes, o clonar uno que existe en un servidor.

  
bash
cd ~/proyectos/tienda
git init                       # crea la carpeta oculta .git: ya es un repositorio

# o bien, traer uno que ya existe (con toda su historia):
git clone https://github.com/ana/tienda.git

  
git init no toca tus archivos. Solo crea una carpeta oculta, .git, donde Git guardará toda la historia. Si borras .git, borras la historia; tus archivos actuales quedan, pero dejan de ser un repositorio.

  
En simple
Un repositorio es tu carpeta de siempre más una carpeta oculta .git con la historia. En el nivel Experto abrimos esa carpeta y vemos qué hay dentro.

  
El comando que más vas a usar

  
git status te dice en qué rama estás y en qué estado está cada archivo. Úsalo antes y después de cada cosa que hagas: es la forma más rápida de no perderte.

  
salida de git status en un repo nuevo

Git en español dice «confirmar» donde casi todo el mundo dice commit. En esta guía usamos los nombres en inglés, que son los que vas a ver en la documentación, en GitHub y en tu equipo. Si prefieres la terminal en inglés: LANG=en_US.UTF-8 git status. Lección 1.4
Las tres áreas: trabajo, staging y repositorio

  
Esta es la idea que más confunde al empezar, y la que más ayuda después. Tus cambios pasan por tres lugares antes de quedar guardados:

  

    
Directorio de trabajoTus archivos, tal como los ves en el editor. Aquí cambias cosas.

    
Staging (índice)Una zona de preparación: lo que pongas aquí es lo que irá en el próximo commit.

    
RepositorioLa historia guardada en .git: cada commit, para siempre.

  

  

  
¿Para qué el paso intermedio? Porque casi nunca cambias una sola cosa. Arreglas un bug, de paso renombras una variable y dejas un console.log de prueba. El staging te deja elegir qué va en cada commit, para que cada uno cuente una sola historia.

  
bash
git add index.html app.js      # agrega dos archivos al staging
git add .                      # agrega todo lo cambiado en esta carpeta y sus subcarpetas
git add -p                     # revisa cada trozo cambiado y elige cuáles agregar
git commit -m "agrega el buscador de productos"

  
git add -p es un superpoderTe muestra cada bloque cambiado y pregunta y (sí), n (no) o s (dividir en partes más chicas). Así un archivo con dos cambios distintos puede ir en dos commits distintos.

  





  
Lección 1.5
Qué es un commit

  
Mucha gente cree que Git guarda las diferencias entre versiones. No: cada commit guarda una foto completa del proyecto. Lo que no cambió no se copia otra vez: el commit nuevo apunta al mismo contenido que ya estaba guardado.

  

  
Además de la foto, cada commit guarda:

  
    
    
  • Su padre: el commit anterior. Así se forma la historia, como una cadena que apunta hacia atrás.
    • 
    
  • Autor y fecha: quién escribió el cambio y cuándo.
    • 
    
  • Mensaje: por qué existe este cambio.
    • 
    
  • Un hash: un identificador como 3f9a2c1, calculado a partir de todo lo anterior. Es su nombre único.
    • 
  

  
En simple
Un commit es una foto completa del proyecto más una nota que dice «vengo de este otro commit». La historia de Git es una cadena de fotos que apuntan hacia atrás.

  
¿Cada cuánto hacer commit?Cada vez que algo funciona y puedes describirlo en una frase. Commits chicos son más fáciles de revisar, de revertir y de entender meses después. «Arregla el total del carrito» es un buen commit; «cambios del martes», no.

  





  
Lección 1.6
Dentro de un commit: blobs, trees y hashes

  
Git guarda todo con solo tres tipos de objeto. Conocerlos explica por qué Git es tan rápido y por qué nunca pierde datos sin avisar.

  

    
ObjetoQué guarda

    
      
BlobEl contenido de un archivo. Solo el contenido: ni el nombre ni la carpeta

      
TreeUna carpeta: la lista de nombres de archivo, sus permisos y el hash de cada blob o subcarpeta

      
CommitEl tree raíz del proyecto, el padre, autor, fecha y mensaje

    
  

  

  
Cada objeto se guarda con el nombre de su hash: un número de 40 caracteres calculado con SHA-1 a partir del contenido. Mismo contenido, mismo hash, siempre y en cualquier computador. Por eso dos archivos idénticos ocupan un solo blob, y por eso si cambia una letra de un archivo, cambia el hash de su blob, de su carpeta y del commit.

  
bash
git cat-file -p HEAD            # el commit actual por dentro
git cat-file -p HEAD^{tree}     # la carpeta raíz de ese commit
git log --oneline               # hashes abreviados: con 7 caracteres basta

  
SHA-256 y Git 3.0SHA-1 ya tiene ataques conocidos, y Git lo usa con detección de colisiones. Git 3.0 (previsto para 2027) creará los repositorios nuevos con SHA-256, de 64 caracteres. Para tu día a día no cambia nada: seguirás usando hashes abreviados.

  





  
Lección 1.7
Ver el historial y los cambios

  
Dos preguntas que te harás todos los días: «¿qué cambié?» y «¿qué pasó antes?». La primera la responde git diff; la segunda, git log.

  

  

    
ComandoCompara

    
      
git diffTu directorio de trabajo con el staging: lo que cambiaste y todavía no agregaste

      
git diff --stagedEl staging con el último commit: lo que entraría si haces commit ahora

      
git diff HEADTu directorio de trabajo con el último commit: todo lo que cambió

      
git diff main featureDos ramas o dos commits cualesquiera

    
  

  
El historial, a tu medida

  
bash
git log --oneline --graph --all     # todo el grafo, una línea por commit
git log -p -2                       # los dos últimos commits con sus cambios
git log --stat                      # qué archivos tocó cada commit
git log --author="Ana" --since="2 weeks ago"
git log -- src/carrito.js           # solo los commits que tocaron ese archivo
git show 3f9a2c1                    # un commit: mensaje y cambios

  
Guárdalo como aliasgit config --global alias.lg "log --oneline --graph --all --decorate" y desde ahora git lg te muestra el grafo completo. Es lo más parecido a las animaciones de esta guía que vas a ver en la terminal.

  
Con q sales del historial, con /texto buscas dentro y con la barra espaciadora avanzas una página.

  





  
Lección 1.8
Ignorar archivos con .gitignore

  
Hay archivos que nunca deben entrar al repositorio: dependencias que se reinstalan (node_modules/), archivos generados (dist/), configuraciones locales y, sobre todo, secretos como .env. Un archivo .gitignore en la raíz le dice a Git que haga como si no existieran.

  

    
Probador de .gitignore

    

      
      
    

    

  

  

    
PatrónQué ignora

    
      
*.logCualquier archivo que termine en .log, en cualquier carpeta

      
dist/Carpetas llamadas dist (la barra final dice «solo carpetas»)

      
/borradoresSolo la de la raíz (la barra inicial ancla el patrón)

      
docs/**/*.pdfPDFs dentro de docs, a cualquier profundidad

      
!.env.exampleExcepción: este sí se versiona, aunque una regla anterior lo ignore

    
  

  
.gitignore no saca lo que ya está versionadoSi un archivo ya entró en un commit, agregarlo a .gitignore no basta. Primero quítalo del índice sin borrarlo del disco: git rm --cached .env. Y si era un secreto que ya subiste, cámbialo: quedó en la historia.

  
Para saber qué regla ignora un archivo: git check-ignore -v ruta/al/archivo. GitHub mantiene plantillas por lenguaje en github/gitignore.

  





  
Lección 1.9
Deshacer lo básico

  
Para deshacer algo, primero pregúntate dónde está lo que quieres deshacer: en tu directorio de trabajo, en el staging o en el último commit. Cada lugar tiene su comando.

  

  

    
Quiero…Comando¿Se pierde algo?

    
      
Descartar lo que cambié en un archivogit restore app.jsSí: los cambios sin guardar se pierden para siempre

      
Sacar un archivo del staginggit restore --staged app.jsNo: los cambios siguen en el archivo

      
Corregir el último commit (mensaje o archivos)git commit --amendNo, pero el commit cambia de hash

      
Borrar archivos nuevos sin seguimientogit clean -n y luego git clean -fSí: -n muestra qué borraría

    
  

  
amend reemplaza, no edita--amend crea un commit nuevo con otro hash. Si ya subiste el commit original y alguien más trabaja sobre él, corregirlo te obliga a reescribir historia compartida. Regla práctica: amend solo antes del push.

  
Vas a ver git checkout -- archivo en tutoriales viejos: hace lo mismo que git restore archivo. restore existe desde Git 2.23 y es más claro, porque checkout hace dos trabajos distintos (cambiar de rama y restaurar archivos).

  





  
Lección 1.10
Mensajes de commit que sirven

  
Un mensaje de commit lo va a leer alguien (tú, en seis meses) que intenta entender por qué el código es como es. La convención que usa casi todo el mundo:

  
    
    
  • Asunto de hasta 50 caracteres (72 como máximo), que diga qué hace el commit: «agrega», «corrige», «elimina».
    • 
    
  • Una línea en blanco.
    • 
    
  • Un cuerpo opcional que explique el porqué y lo que no es obvio. El qué ya lo muestra el diff.

Revisor de mensajes

    Ramas y equipo
    Ramas, fusiones y conflictos, y cómo trabajar con un repositorio remoto: fetch, pull, push y pull requests. Lo que necesitas para trabajar con otras personas sin miedo a romper nada.
    
  
    
    
    
    
    


    
  
    Lección 2.1
    Qué es una rama de verdad
    
  
    En otros sistemas, crear una rama copia el proyecto entero. En Git, una rama es un nombre que apunta a un commit. Nada más. Por eso crear una rama es instantáneo, y por eso en Git se crean ramas para todo.
    
  
    
  
    En simple
    Los commits son la historia; las ramas son post-its pegados en algunos commits. Cuando haces commit, el post-it de la rama en la que estás se mueve al commit nuevo.
    
  
    bash
    git branch                    # lista las ramas; * marca la actual
git branch feature            # crea una rama (no te cambia a ella)
git switch -c feature         # crea y cambia en un solo paso
git branch -m viejo nuevo     # renombra
git branch -d feature         # borra (si ya está fusionada; -D fuerza)
    
  
    Ahora pruébalo tú. Escribe los comandos en la terminal del laboratorio y mira cómo se mueven las etiquetas:
    
  
    
  

    


    
  
    Lección 2.2
    HEAD y cambiar de rama
    
  
    HEAD es la respuesta de Git a «¿dónde estoy?». Normalmente apunta a una rama (HEAD → main), y esa rama apunta a un commit. Cuando cambias de rama, Git mueve HEAD y deja tus archivos como estaban en el commit de esa rama.
    
  
    
  
    bash
    git switch feature        # cambia a feature
git switch -              # vuelve a la rama anterior (como cd -)
git switch -c arreglo     # crea arreglo desde donde estás y cambia a ella
    
  
    switch o checkoutgit checkout feature hace lo mismo y sigue existiendo: no está deprecado y no se va a eliminar. Desde Git 2.23, switch (cambiar de rama) y restore (restaurar archivos) separan sus dos trabajos, y los errores son más claros. Esta guía usa switch.
    
  
    Si Git se niega a cambiar de ramaTienes cambios sin guardar en un archivo que es distinto en la otra rama, y cambiar los pisaría. Haz commit, guárdalos con git stash (lección 2.9) o descártalos. Los cambios que no chocan viajan contigo a la otra rama.
    
  

    


    
  
    Lección 2.3
    Fusionar: fast-forward
    
  
    Terminaste tu trabajo en feature y quieres llevarlo a main. Te cambias a main y ejecutas git merge feature. Lo que pasa depende de la forma del grafo.
    
  
    El caso más simple: nadie tocó main desde que creaste feature. Entonces no hay nada que combinar: Git solo adelanta la etiqueta main hasta el último commit de feature. Se llama fast-forward.
    
  
    
  
    bash
    git switch main
git merge feature            # fast-forward si se puede; si no, commit de merge
git merge --no-ff feature    # siempre crea un commit de merge (deja registro de la rama)
git merge --ff-only feature  # solo si es fast-forward; si no, falla sin tocar nada
    
  
    En simple
    Fast-forward = «main estaba atrás, ahora está adelante». No se crea ningún commit: solo se mueve una etiqueta.
    
  

    


    
  
    Lección 2.4
    Merge de tres vías
    
  
    Ahora el caso real: mientras trabajabas en feature, alguien agregó commits a main. Las historias divergieron. Git busca el último commit que ambas ramas tienen en común (la base), mira qué cambió cada lado desde ahí y combina los dos conjuntos de cambios en un commit de merge, que tiene dos padres.
    
  
    
  
    Se llama «de tres vías» porque compara tres versiones: la base, tu rama y la otra. Si un lado cambió un archivo y el otro no, gana el cambio. Si los dos cambiaron partes distintas del mismo archivo, Git junta ambas. Solo si los dos cambiaron las mismas líneas de forma distinta, te pregunta: eso es un conflicto (siguiente lección).
    
  
    
  
    La estrategia ortDesde Git 2.34, el algoritmo de merge por defecto se llama ort. Por eso ves «Merge made by the 'ort' strategy». Es más rápido y maneja mejor los archivos renombrados que el anterior, recursive.
    
  

    


    
  
    Lección 2.5
    Conflictos sin pánico
    
  
    Un conflicto no es un error: es Git diciendo «las dos ramas cambiaron lo mismo de forma distinta, y no me corresponde a mí decidir». Git deja el merge a medias, marca el archivo y espera a que elijas.
    
  
    
  
    Leer los marcadores
    
  
    precio.js durante el conflicto
    <<<<<<< HEAD
const precio = 120;
=======
const precio = 95;
>>>>>>> feature
    
  
    Arriba de ======= está tu versión (la de HEAD, la rama en la que estás); abajo, la que llega de la otra rama. Tu trabajo: dejar el archivo como debe quedar y borrar los tres marcadores. Practícalo:
    
  
    
    
    Resuelve el conflicto
    
    
    
      
    
        
        
        
        
      
    
      
      
    
    
    
  
    
  
    El flujo completo
    
  
    bash
    git merge feature          # CONFLICT (content): Merge conflict in precio.js
git status                 # "both modified: precio.js"
# edita el archivo, deja el resultado correcto y borra los marcadores
git add precio.js          # marca el archivo como resuelto
git commit                 # crea el commit de merge (el mensaje ya viene escrito)

git merge --abort          # o vuelve atrás como si nada hubiera pasado
    
  
    Nuevo en Git 2.56: git add --resolvedAgrega al staging los archivos que tenían conflicto, sin arrastrar otros cambios sin relación, y antes revisa que no queden marcadores: si encuentra alguno, se detiene sin agregar nada. Útil cuando el merge toca muchos archivos.
    
  
    Menos conflictos, más chicosIntegra seguido (ramas de días, no de semanas), haz commits chicos y no mezcles cambios de formato con cambios de lógica. Para ver también la versión base en los marcadores: git config --global merge.conflictStyle zdiff3.
    
  

    


    
  
    Lección 2.6
    Remotos: clone, origin y ramas remotas
    
  
    Un remoto es otra copia del repositorio, normalmente en un servidor como GitHub. Cuando clonas, Git llama origin al remoto de donde viene, y crea dos cosas que conviene distinguir:
    
  
    
    
    mainTu rama local. Se mueve cuando tú haces commit, merge o reset.
    
    
    origin/mainUna rama remota: tu recuerdo de dónde estaba main en GitHub la última vez que preguntaste. Solo se mueve con fetch, pull o push.
    
    
    UpstreamLa conexión entre las dos: main «sigue» a origin/main. Así Git sabe si vas adelante o atrás.
    
  
    
  
    
  
    bash
    git remote -v                   # remotos y sus URL
git branch -vv                  # cada rama con su upstream y si va adelante o atrás
git remote add origin git@github.com:ana/tienda.git   # conectar un repo creado con init
    
  
    HTTPS o SSHCon HTTPS, GitHub pide un token (no tu contraseña) o un gestor de credenciales; Git for Windows y GitHub CLI (gh auth login) lo configuran solos. Con SSH generas una llave una vez (ssh-keygen -t ed25519), la agregas a tu cuenta y no vuelves a escribir nada.
    
  

    


    
  
    Lección 2.7
    fetch, pull y push
    
  
    Git nunca habla con el servidor por su cuenta. Tres comandos mueven commits entre tu repositorio y el remoto:
    
  
    
    
    ComandoQué hace¿Toca tus ramas?
    
    
      
    git fetchDescarga commits nuevos y mueve origin/*No. Siempre seguro
    
      
    git pullfetch y después integra origin/tu-rama en tu ramaSí: merge, rebase o fast-forward
    
      
    git pushSube tus commits y mueve tu rama en el servidorMueve la del servidor
    
        
  
    
  
    
  
    bash
    git fetch                       # mira qué hay de nuevo sin tocar nada
git log main..origin/main       # qué commits llegaron
git pull                        # trae e integra
git push                        # sube
git push -u origin feature      # primera vez de una rama: crea y conecta el upstream
    
  
    pull con historias distintasSi tú tienes commits locales y el servidor también, git pull tiene que combinarlos. Con pull.rebase true tus commits se reaplican encima (historia lineal); con false, se crea un commit de merge. Si no lo configuraste, Git te pide elegir. Lo configuraste en la lección 1.2.
    
  

    


    
  
    Lección 2.8
    Cuando push es rechazado
    
  
    Tarde o temprano verás esto:
    
  
    salida
     ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:ana/tienda.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.
    
  
    No es un error tuyo: alguien subió commits que tú no tienes. Si Git aceptara tu push, su trabajo desaparecería del servidor. Por eso solo acepta pushes que avanzan la rama remota (fast-forward).
    
  
    
  
    bash
    git pull --rebase     # trae lo nuevo y pone tus commits encima
git push              # ahora sí es un avance
    
  
    No fuerces en ramas compartidasgit push --force reemplaza la rama del servidor por la tuya, y borra lo que otros subieron. En tu propia rama, tras un rebase, a veces hace falta forzar: usa --force-with-lease (lección 3.9), que se niega si hay trabajo ajeno que no viste.
    
  

    


    
  
    Lección 2.9
    Guardar a medias: stash
    
  
    Estás a mitad de algo y te piden un arreglo urgente en otra rama. No quieres hacer un commit de «wip» ni perder lo que llevas. git stash guarda tus cambios en una pila y deja el directorio de trabajo limpio.
    
  
    
  
    bash
    git stash push -m "búsqueda a medias"   # guarda y limpia
git stash -u                            # incluye archivos nuevos sin seguimiento
git stash list                          # stash@{0}, stash@{1}...
git stash pop                           # aplica el último y lo quita de la pila
git stash apply stash@{1}               # aplica uno y lo deja en la pila
git stash drop stash@{1}                # borra uno
    
  
    Úsalo como bolsillo, no como cajónUn stash es fácil de olvidar: no tiene rama y su nombre es un número. Para algo que va a durar más de un rato, mejor una rama con un commit temporal, o un worktree (nivel Experto).
    
  

    


    
  
    Lección 2.10
    Tags y versiones
    
  
    Un tag es como una rama que nunca se mueve: un nombre fijo para un commit. Se usa para marcar versiones publicadas: v1.0.0, v1.1.0. En los grafos de esta guía, los tags son las etiquetas blancas.
    
  
    bash
    git tag -a v1.2.0 -m "Versión 1.2.0"    # tag anotado: con autor, fecha y mensaje
git tag v1.2.0-beta                     # tag liviano: solo el nombre
git tag -l "v1.*"                       # lista
git push origin v1.2.0                  # los tags no suben con un push normal
git push --tags                         # sube todos
git switch --detach v1.2.0              # mira el código de esa versión
    
  
    Usa tags anotados para versiones: guardan quién y cuándo, y se pueden firmar. La convención más común para los números es versionado semántico (MAYOR.MENOR.PARCHE): sube MAYOR si rompes compatibilidad, MENOR si agregas funciones, PARCHE si solo corriges.
    
  
    Releases en GitHubUn «Release» de GitHub es un tag más notas y archivos descargables. Crea el tag con Git (o desde la interfaz) y GitHub arma la página.
    
  

    


    
  
    Lección 2.11
    El flujo con pull requests
    
  
    Casi todos los equipos trabajan igual: nadie hace commit directo en main. Cada cambio vive en su rama, se sube, y se propone con un pull request (en GitLab, merge request), donde otras personas lo revisan y las pruebas automáticas lo validan antes de fusionarlo.
    
  
    
  
    bash
    git switch main && git pull          # parte desde main al día
git switch -c login-google           # una rama por cambio
# ... commits ...
git push -u origin login-google      # súbela y abre el pull request en GitHub
# ... revisión: más commits y git push actualizan el mismo PR ...
git switch main && git pull          # después del merge, trae main
git branch -d login-google           # y borra tu rama local
    
  
    
    
    Botón de merge en GitHubResultado en main
    
    
      
    Create a merge commitTodos tus commits más un commit de merge
    
      
    Squash and mergeUn solo commit con todos tus cambios (el más común)
    
      
    Rebase and mergeTus commits copiados encima de main, sin commit de merge
    
        
  
    
  
    Con squash, borra tu rama despuésTras un «Squash and merge», tus commits originales no están en main (está su resumen). Si sigues trabajando en la misma rama, la próxima PR va a mostrar los cambios viejos otra vez. Rama nueva para cada cambio. Desde Git 2.56, git branch --delete-merged origin limpia las ramas locales ya fusionadas.

    03
    Nivel 03 · Avanzado
    Reescribir y rescatar
    Rebase, rebase interactivo, cherry-pick, reset y revert para dar forma a la historia, y reflog, bisect y force push seguro para salir de cualquier lío. Aquí se pierde el miedo a Git.
    
  
    
    
    
    
    


    
  
    Lección 3.1
    Rebase: mover commits a otra base
    
  
    Tu rama feature salió de main hace unos días, y main avanzó. Con merge juntarías las dos historias. Con rebase haces otra cosa: tomas tus commits y los vuelves a aplicar, uno por uno, encima del main actual, como si hubieras empezado tu rama hoy.
    
  
    
  
    El detalle clave: los commits de un rebase son copias nuevas. Tienen el mismo cambio y el mismo mensaje, pero otro padre, y por lo tanto otro hash. Los originales no se borran: quedan sin rama que los apunte, y el reflog los recuerda.
    
  
    bash
    git switch feature
git rebase main             # reaplica tus commits encima de main
# si hay conflicto: resuélvelo, git add, y luego
git rebase --continue       # sigue con el próximo commit
git rebase --abort          # o vuelve a como estaba todo antes
    
  
    La regla de oroNo hagas rebase de commits que otras personas ya tienen. Si alguien basó trabajo en tus commits originales y tú los reemplazas por copias, sus historias y la tuya ya no coinciden. Rebase sí, pero en tu rama, antes de compartirla (o en una rama solo tuya).
    
  
    
  

    


    
  
    Lección 3.2
    ¿Merge o rebase?
    
  
    Las dos integran cambios; la diferencia es cómo queda la historia. Merge conserva lo que pasó de verdad (dos líneas que se unen). Rebase cuenta una historia más simple (una sola línea), a costa de reescribir tus commits.
    
  
    
  
    
    
    MergeRebase
    
    
      
    HistoriaReal, con bifurcacionesLineal, más fácil de leer
    
      
    HashesNo cambianTus commits cambian de hash
    
      
    ConflictosSe resuelven una vezPueden aparecer en cada commit reaplicado
    
      
    Seguro en ramas compartidasSíNo
    
        
  
    
  
    Una regla que funciona
    Usa rebase para actualizar tu rama con lo último de main antes de abrir o actualizar tu pull request. Usa merge (o squash) para integrar la rama terminada en main. Así tu rama se lee limpia y main nunca se reescribe.
    
  

    


    
  
    Lección 3.3
    Rebase interactivo: limpiar antes de compartir
    
  
    Mientras trabajas, haces commits como «wip», «arregla typo» o «ahora sí». Está bien: son tu borrador. Antes de pedir revisión, el rebase interactivo te deja editar esa serie: unir commits, cambiar mensajes, reordenarlos o borrarlos.
    
  
    
  
    bash
    git rebase -i main          # edita todos los commits de tu rama que no están en main
git rebase -i HEAD~4        # o los últimos cuatro
    
  
    
    
    PalabraQué hace con ese commit
    
    
      
    pick (p)Lo deja tal cual
    
      
    reword (r)Lo deja, pero te deja cambiar el mensaje
    
      
    edit (e)Se detiene ahí para que cambies el contenido (luego git rebase --continue)
    
      
    squash (s)Lo une al commit de arriba y te deja combinar los mensajes
    
      
    fixup (f)Lo une al de arriba y descarta su mensaje
    
      
    drop (d)Lo elimina
    
        
  
    
  
    En el editor, el commit más viejo va arriba (al revés que en git log). Para reordenar, mueve las líneas.
    
  
    Correcciones que se acomodan solas
    
  
    bash
    git commit --fixup=a1b2c3d          # "fixup! ..." : corrige un commit anterior
git rebase -i --autosquash main     # coloca y marca los fixup automáticamente
git config --global rebase.autoSquash true   # siempre
    
  
    Nuevo: git history (experimental)
    
  
    Git 2.54 agregó git history para las ediciones más comunes sin abrir un rebase interactivo. Git 2.55 sumó fixup y 2.56, drop. Por diseño, aborta si la operación generaría un conflicto, y todavía no funciona con historias que tienen merges.
    
  
    bash
    git history reword a1b2c3d     # cambia el mensaje de ese commit
git history split a1b2c3d      # divide un commit en dos, eligiendo trozos
git history fixup a1b2c3d      # mete lo que está en staging dentro de ese commit
git history drop a1b2c3d       # lo elimina y reaplica los que venían después
    
  

    


    
  
    Lección 3.4
    Cherry-pick: copiar un commit
    
  
    A veces no quieres una rama entera, solo un commit. El caso típico: arreglaste un bug en main y necesitas el mismo arreglo en release/1.0, sin traer todo lo nuevo. git cherry-pick copia ese cambio y lo aplica encima de tu rama actual.
    
  
    
  
    bash
    git switch release/1.0
git cherry-pick -x a1b2c3d      # -x anota de qué commit viene la copia
git cherry-pick A^..B           # una serie de commits (de A a B, incluidos)
git cherry-pick --abort         # si hay conflicto y prefieres no seguir
    
  
    No lo uses para todoCada cherry-pick crea un commit duplicado (mismo cambio, otro hash). Si después fusionas las dos ramas, Git normalmente lo nota, pero la historia queda confusa. Para traer muchos commits, merge o rebase.
    
  
    
  

    


    
  
    Lección 3.5
    Reset: soft, mixed y hard
    
  
    git reset asusta porque hace tres cosas distintas según la opción. Todo se aclara con las tres áreas de la lección 1.4: reset mueve la rama actual a otro commit, y luego, según el modo, iguala también el staging y el directorio de trabajo.
    
  
    
  
    
    
    ModoRamaStagingDirectorio de trabajo
    
    
      
    --softSe mueveIgualIgual
    
      
    --mixed (por defecto)Se mueveSe iguala al commitIgual
    
      
    --hardSe mueveSe iguala al commitSe iguala al commit: lo no guardado se pierde
    
        
  
    
  
    bash
    git reset --soft HEAD~1      # deshace el commit; los cambios quedan listos en staging
git reset HEAD~1             # deshace el commit; los cambios quedan sin agregar
git reset --hard HEAD~1      # deshace el commit y sus cambios
git reset --hard origin/main # deja tu main idéntico al del servidor
    
  
    --hard borra de verdad lo que no estaba guardadoLos commits que «deshaces» se recuperan con el reflog. Pero los cambios que no estaban en ningún commit ni en el staging desaparecen sin rastro. Antes de un --hard, un git status.
    
  

    


    
  
    Lección 3.6
    Revert: deshacer sin reescribir
    
  
    Si el commit que quieres deshacer ya está en una rama compartida, no lo borres: contrarréstalo. git revert crea un commit nuevo que aplica el cambio inverso. La historia no se reescribe, nadie tiene que hacer nada especial y se sube con un push normal.
    
  
    
  
    bash
    git revert a1b2c3d          # abre el editor con 'Revert "..."'
git revert --no-edit HEAD   # sin abrir el editor
git revert -m 1 <merge>     # revertir un merge: -m 1 dice qué padre es "la línea principal"
    
  
    Reset o revert
    ¿El commit está solo en tu máquina? Reset (o rebase). ¿Ya lo tiene alguien más? Revert.
    
  
    
  

    


    
  
    Lección 3.7
    Reflog: la red de seguridad
    
  
    Casi nada se pierde en Git. Cada vez que HEAD o una rama se mueve (commit, reset, rebase, switch, merge), Git lo anota en el reflog. Si «perdiste» commits con un reset o un rebase, el reflog sabe dónde estaban.
    
  
    
  
    bash
    git reflog                       # HEAD@{0} es ahora, HEAD@{1} el paso anterior...
git reflog show feature          # el de una rama
git reset --hard HEAD@{1}        # vuelve a donde estabas antes del último movimiento
git branch rescate HEAD@{4}      # o crea una rama en ese punto, sin tocar nada más
git log -g --oneline main@{yesterday}..main   # qué cambió en main desde ayer
    
  
    
    
    Lo que el reflog sí guardaLo que no
    
    
      
    Commits a los que apuntó HEAD o una rama, durante 90 días (30 si quedaron inalcanzables)Cambios que nunca entraron en un commit ni en el staging
    
      
    Solo en tu máquinaNo viaja con push: el reflog de un compañero no te sirve a ti
    
        
  
    
  
    
  

    


    
  
    Lección 3.8
    HEAD separado (detached)
    
  
    Si te cambias a un commit o a un tag en vez de a una rama, HEAD apunta directo a ese commit. Git dice «You are in 'detached HEAD' state». No es un error: es el modo para mirar una versión vieja o probar algo. El único riesgo es hacer commits ahí y luego irte.
    
  
    
  
    bash
    git switch --detach v1.2.0     # mira el código de esa versión
git switch -c experimento      # ¿hiciste commits que quieres guardar? crea una rama aquí
git switch -                   # vuelve a tu rama
    
  
    Si ya te fuisteGit te avisó: «Warning: you are leaving 2 commits behind» e imprimió el hash. Créale una rama: git branch experimento a1b2c3d. ¿No lo copiaste? Está en git reflog.
    
  

    


    
  
    Lección 3.9
    Push forzado sin pisar a nadie
    
  
    Después de un rebase o un amend en tu rama, el servidor tiene la versión vieja y tu push normal es rechazado (no es un avance). Tienes que forzarlo. La pregunta es cómo.
    
  
    
  
    bash
    git push --force-with-lease                     # fuerza solo si nadie subió algo nuevo
git push --force-with-lease --force-if-includes # además exige que hayas integrado lo que viste
git config --global alias.pushf "push --force-with-lease --force-if-includes"
    
  
    --force-with-lease compara la rama del servidor con tu origin/feature: si coinciden, nadie subió nada desde tu último fetch y es seguro reemplazarla. Si no, se niega. El problema: un git fetch en segundo plano (tu editor lo hace) actualiza origin/feature sin que veas los commits nuevos. --force-if-includes cierra ese hueco.
    
  
    Protege main en el servidorEn GitHub y GitLab activa la protección de ramas (o rulesets) en main: prohíbe force push y exige pull request. Así un error local nunca reescribe la rama de todos.
    
  

    


    
  
    Lección 3.10
    Bisect: encontrar el commit culpable
    
  
    Algo funcionaba hace dos semanas y hoy no, y entre medio hay 200 commits. git bisect hace una búsqueda binaria: te lleva al commit del medio, le dices si está bien o mal, y descarta la mitad. Con 200 commits, encuentra al culpable en unos 8 pasos.
    
  
    
  
    bash
    git bisect start
git bisect bad                 # el commit actual está mal
git bisect good v2.3           # esta versión funcionaba
# Git te cambia a un commit intermedio: pruébalo y responde
git bisect good                # o: git bisect bad · git bisect skip si no se puede probar
# ... hasta: "a1b2c3d is the first 'bad' commit"
git bisect reset               # vuelve a donde estabas

git bisect run npm test        # o automatízalo con cualquier comando
    
  
    Con bisect run, el código de salida decide: 0 es bueno, de 1 a 127 es malo (salvo 125, que significa «no se puede probar, sáltalo»). Un script de diez líneas que reproduce el bug encuentra el culpable mientras tomas un café.
    
  

    


    
  
    Lección 3.11
    Investigar el código con Git
    
  
    Git sabe mucho más que «qué cambió». Bien preguntado, te dice quién escribió cada línea, cuándo apareció una función o por qué existe un if raro.
    
  
    bash
    git blame -L 40,60 src/carrito.js    # quién cambió cada línea, y en qué commit
git blame -w -C src/carrito.js       # ignora espacios y sigue código movido entre archivos
git log -S "calcularIVA" --oneline   # commits que agregaron o quitaron ese texto
git log -G "descuento\s*=" -p        # commits cuyo diff coincide con una regex
git log -L :calcularIVA:src/iva.js   # la historia de una función
git grep -n "TODO" main              # busca en los archivos de una rama
git range-diff main feature@{1} feature   # cómo cambió tu serie antes y después del rebase
    
  
    Que blame ignore los commits de formatoSi tu equipo hizo un commit gigante de formato, todo blame apunta a él. Pon sus hashes en un archivo .git-blame-ignore-revs y configura git config blame.ignoreRevsFile .git-blame-ignore-revs. GitHub lo respeta automáticamente.

    Git por dentro
    Abre la carpeta .git y mira cómo están hechos los commits, las ramas y los packfiles. Después, las herramientas para trabajar a escala: worktrees, hooks, repos gigantes, submódulos, estrategias de equipo y lo que trae Git 3.0.
    
  
    
    
    
    
    


    
  
    Lección 4.1
    La carpeta .git por dentro
    
  
    Todo lo que Git sabe de tu proyecto está en .git, y casi todo son archivos de texto que puedes leer. Cuando lo ves, desaparece la magia: una rama es literalmente un archivo con un hash.
    
  
    
  
    
    
    RutaQué es
    
    
      
    HEADDónde estás: ref: refs/heads/main, o un hash si HEAD está separado
    
      
    refs/heads/Tus ramas: un archivo por rama con el hash al que apunta
    
      
    refs/remotes/, refs/tags/Ramas remotas y tags, igual
    
      
    objects/Todos los commits, trees y blobs, por hash (sueltos o en packfiles)
    
      
    indexEl staging, en formato binario
    
      
    logs/El reflog
    
      
    config, hooks/Configuración del repo y scripts de hooks
    
        
  
    
  
    bash
    cat .git/HEAD
cat .git/refs/heads/main
git cat-file -t 3f9a2c1      # qué tipo de objeto es
git rev-parse main           # el hash completo de una rama
git count-objects -vH        # cuántos objetos hay y cuánto ocupan
    
  
    Plumbing y porcelainGit tiene dos capas de comandos. Los de «porcelana» (commit, switch, merge) son para personas. Los de «fontanería» (cat-file, hash-object, update-ref, rev-parse) son las piezas con las que se construyen los anteriores, y son estables para usarlos en scripts.
    
  

    


    
  
    Lección 4.2
    Hashes en cadena
    
  
    Cada commit incluye el hash de su padre, y el hash de un commit se calcula con todo lo que contiene. Esa cadena tiene una consecuencia enorme: si cambias cualquier cosa de un commit viejo, cambia su hash, y con él el de todos los que vienen después.
    
  
    
  
    Esto explica dos cosas que ya viste. Por qué reescribir historia (amend, rebase) siempre crea commits nuevos: no hay forma de «editar» uno sin cambiar su identidad. Y por qué con el hash del último commit basta para verificar toda la historia: si alguien alterara un byte en el pasado, los hashes dejarían de coincidir. A esta estructura se le llama árbol de Merkle.
    
  
    En simple
    Un hash de commit es la huella de ese commit y de todo su pasado. Dos repositorios con el mismo hash en main tienen exactamente la misma historia.
    
  

    


    
  
    Lección 4.3
    Objetos sueltos y packfiles
    
  
    Cuando haces commit, cada objeto nuevo se guarda como un archivo comprimido aparte (un objeto «suelto»). Con el tiempo serían miles. Git los junta periódicamente en packfiles: un solo archivo donde las versiones parecidas de un mismo archivo se guardan como diferencias (deltas) de otra.
    
  
    
  
    bash
    git count-objects -vH       # objetos sueltos, packs y tamaño
git gc                      # compacta a mano (Git lo hace solo de vez en cuando)
git maintenance start       # programa mantenimiento en segundo plano
git maintenance run --task=gc
    
  
    Los packfiles también son lo que viaja por la red: fetch, clone y push negocian qué objetos le faltan a cada lado y mandan un pack con solo eso. Por eso clonar un repo con años de historia es más rápido de lo que parece.
    
  
    Archivos binarios grandesLos deltas funcionan mal con videos, imágenes pesadas o modelos de datos: cada versión pesa casi completa y el repositorio crece sin parar. Para eso existe Git LFS, que guarda esos archivos fuera del repositorio y deja en Git solo un puntero.
    
  

    


    
  
    Lección 4.4
    Worktrees: varias ramas a la vez
    
  
    Cambiar de rama obliga a guardar o hacer stash de lo que llevas. Un worktree es otra carpeta de trabajo conectada al mismo repositorio, con su propia rama. Puedes tener main en una carpeta, un hotfix en otra y la revisión de un PR en una tercera, todo al mismo tiempo.
    
  
    
  
    bash
    git worktree add ../tienda-hotfix -b hotfix/pago   # carpeta nueva con rama nueva
git worktree add ../tienda-review origin/feature-x  # revisar un PR sin tocar tu trabajo
git worktree list
git worktree remove ../tienda-hotfix
git worktree prune                                  # limpia worktrees borrados a mano
    
  
    Comparten objetos, ramas, stash y configuración: un commit hecho en un worktree aparece en el historial de todos. Lo único que no comparten es lo que está a medias en cada carpeta. Son ideales para dejar trabajando a un agente de IA en una rama mientras tú sigues en otra.
    
  
    Una rama, un worktreeGit no deja tener la misma rama en dos worktrees a la vez, porque un commit en uno dejaría desactualizado al otro. Si lo necesitas para mirar, usa --detach.
    
  

    


    
  
    Lección 4.5
    Hooks de Git
    
  
    Un hook es un script que Git ejecuta en un momento concreto: antes de crear un commit, al escribir el mensaje, antes de un push. Si un hook «de antes» termina con error, Git cancela la operación. Sirven para que nadie suba código sin formatear, con tests rotos o con mensajes fuera de formato.
    
  
    
  
    
    
    HookCuándo correUso típico
    
    
      
    pre-commitAntes de crear el commitFormateo, lint, tests rápidos, buscar secretos
    
      
    commit-msgCon el mensaje escritoValidar Conventional Commits o un ID de ticket
    
      
    pre-pushAntes de subirTests más lentos
    
      
    post-checkout, post-mergeDespués de cambiar de rama o fusionarReinstalar dependencias si cambió el lockfile
    
        
  
    
  
    Los hooks viven en .git/hooks/, que no se versiona: cada persona tendría que instalarlos. Los equipos los guardan en el repositorio y apuntan Git ahí con core.hooksPath, o usan herramientas como husky, lefthook o pre-commit. Las versiones recientes de Git también permiten declarar hooks directamente en la configuración, e incluso correr varios en paralelo:
    
  
    bash
    git config core.hooksPath .githooks            # hooks versionados en .githooks/

# hooks declarados en la configuración (ver git help hook)
git config set hook.lint.command "npm run lint"
git config set --append hook.lint.event pre-commit
    
  
    Los hooks locales se pueden saltargit commit --no-verify no ejecuta pre-commit ni commit-msg. Por eso lo importante se valida también en el servidor: reglas de protección de rama y CI (GitHub Actions, GitLab CI) que bloquean el merge si algo falla.
    
  

    


    
  
    Lección 4.6
    Repos gigantes: partial clone y sparse-checkout
    
  
    En un monorepo con años de historia y cientos de carpetas, clonar todo puede tardar horas y llenar el disco. No necesitas todo: Git puede descargar menos y mostrarte menos.
    
  
    
  
    
    
    TécnicaQué recortaCuándo
    
    
      
    --filter=blob:none (partial clone)Descarga commits y carpetas, pero el contenido de cada archivo recién cuando lo necesitasDesarrollo diario en repos grandes
    
      
    sparse-checkoutDeja en disco solo las carpetas que eliges; la historia sigue completaMonorepos donde trabajas en una parte
    
      
    --depth 1 (shallow clone)Solo los últimos commitsCI y despliegues; mala idea para desarrollar
    
        
  
    
  
    bash
    git clone --filter=blob:none https://github.com/org/monorepo.git
cd monorepo
git sparse-checkout set apps/web services/pagos
git sparse-checkout add docs

scalar clone https://github.com/org/monorepo.git   # todo lo anterior, más mantenimiento
    
  
    scalar viene incluido con Git y configura un repo grande con las opciones recomendadas: partial clone, sparse-checkout, mantenimiento en segundo plano y monitor de archivos.
    
  

    


    
  
    Lección 4.7
    Submódulos y subtree
    
  
    A veces un repositorio necesita incluir otro: una librería de componentes compartida, un tema, un SDK. Hay dos formas, con filosofías opuestas.
    
  
    
  
    bash
    git submodule add https://github.com/org/ui.git vendor/ui
git clone --recurse-submodules https://github.com/org/app.git
git submodule update --init --recursive      # si clonaste sin la opción anterior
git submodule update --remote vendor/ui      # trae lo último del submódulo
git add vendor/ui && git commit -m "actualiza ui"   # y fija el nuevo puntero
    
  
    
    
    SubmóduloSubtree
    
    
      
    Qué guarda el repo padreUn puntero a un commit del otro repoUna copia de los archivos
    
      
    ClonarNecesita --recurse-submodulesNormal
    
      
    Bueno paraDependencias con su propio ciclo y versiones exactasIncluir código que rara vez cambia, sin pasos extra
    
        
  
    
  
    Antes de elegir cualquieraSi el otro repositorio publica paquetes (npm, PyPI, Maven), un administrador de paquetes casi siempre es mejor opción que submódulos o subtree.
    
  

    


    
  
    Lección 4.8
    Estrategias de ramas en equipo
    
  
    Git no impone cómo organizar las ramas. Cada equipo elige una estrategia, y la elección depende sobre todo de cada cuánto despliegan.
    
  
    
  
    
    
    EstrategiaCómo funcionaPara quién
    
    
      
    Trunk-basedTodos integran a main a diario con ramas de horas; lo incompleto se esconde con feature flagsEquipos con CI sólido que despliegan varias veces al día
    
      
    GitHub flowmain siempre desplegable; una rama y un PR por cambioLa mayoría de los equipos web
    
      
    Git flowRamas develop, release/* y hotfix/*, y main con tags de versiónSoftware con versiones numeradas y soporte largo (apps de escritorio, librerías)
    
        
  
    
  
    Si dudas
    Empieza con GitHub flow: ramas cortas, pull requests y main protegida. Es simple, funciona con equipos de cualquier tamaño y puedes acercarte a trunk-based a medida que mejoran tus pruebas automáticas. Compara todas las estrategias, con animaciones y un asistente para elegir, en Estrategias de ramas.
    
  

    


    
  
    Lección 4.9
    Firmar commits y seguridad
    
  
    Cualquiera puede poner tu nombre y correo en un commit: user.name es solo texto. Firmar tus commits prueba que salieron de tu llave. GitHub y GitLab los marcan como «Verified». La forma más simple hoy es firmar con tu llave SSH.
    
  
    bash
    git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true
# y agrega la misma llave en GitHub como "Signing key"
git log --show-signature -1
    
  
    Hábitos de seguridad
    
  
      
    
    • Nunca subas secretos. Usa .gitignore, variables de entorno y un escáner en pre-commit. Si se te escapa uno, rótalo primero: borrarlo de la historia no deshace que ya estuvo expuesto.
      • 
    
    • Borrar de la historia se hace con git filter-repo (herramienta aparte, recomendada por el propio proyecto Git en lugar de filter-branch), y requiere coordinar un force push con todo el equipo.
      • 
    
    • Desconfía de repositorios ajenos: un repo puede traer hooks o configuración que ejecute código. Git no copia los hooks al clonar, y safe.directory evita usar repos de otros usuarios del sistema. En Git 3.0, safe.bareRepository pasará a explicit para cerrar otro truco con repos «desnudos».
      • 
  
    
  

    


    
  
    Lección 4.10
    Configuración pro y Git 3.0
    
  
    Unas pocas opciones hacen a Git más cómodo y más seguro. Ninguna cambia cómo funciona; solo ajustan valores por defecto pensados para no romper hábitos de hace quince años.
    
  
    ~/.gitconfig
    [rerere]
	enabled = true          # recuerda cómo resolviste un conflicto y lo repite
[merge]
	conflictStyle = zdiff3  # los marcadores muestran también la versión base
[diff]
	algorithm = histogram   # diffs más legibles
	colorMoved = default    # el código movido se pinta distinto
[push]
	autoSetupRemote = true  # el primer push de una rama crea su upstream
[fetch]
	prune = true            # borra origin/* de ramas que ya no existen
[rebase]
	autoSquash = true
	updateRefs = true       # mueve también las ramas apiladas encima
[branch]
	sort = -committerdate   # git branch: las más recientes primero
    
  
    rerere («reuse recorded resolution») merece una mención aparte: si resuelves el mismo conflicto varias veces (por ejemplo, al hacer rebase seguido de una rama larga), Git aprende tu resolución y la aplica sola.
    
  
    Lo que trae Git 3.0
    
  
    El proyecto Git anunció la transición: la versión de diciembre de 2026 se llama 2.98, y en 2027 llegan la 2.99 (de soporte largo) y Git 3.0. Los cambios afectan a repositorios nuevos; los que ya tienes siguen funcionando.
    
  
    
    
    CambioQué significa para ti
    
    
      
    SHA-256 por defectoHashes de 64 caracteres en repos nuevos. Los repos SHA-1 siguen soportados
    
      
    Reftable por defectoLas refs se guardan en una tabla y no en un archivo por rama: más rápido y sin problemas con mayúsculas en macOS y Windows. Pruébalo hoy con init.defaultRefFormat=reftable
    
      
    main como rama inicialLo que ya configuraste en la lección 1.2
    
      
    Comandos retiradosgit whatchanged (usa git log --raw), pack-redundant y los grafts (usa git replace)
    
      
    Lo que se quedagit checkout no se elimina ni se depreca

    Prácticas que funcionan con cualquier estrategia
    
    
    
      
    Merge queueCada PR se prueba junto con main y con los que entran antes, y solo se fusiona si todo pasa. Evita el «main roto» cuando muchos fusionan a la vez. GitHub la tiene como merge queue (escucha el evento merge_group en tus workflows) y GitLab como merge trains.
    
      
    Ship / Show / AskNo todo cambio necesita esperar revisión. Ship: va directo a main. Show: PR que se fusiona sin esperar y se revisa después. Ask: PR que espera la revisión. Propuesto por Rouan Wilsenach en martinfowler.com; requiere confianza y buen CI.
    
      
    main protegidaPull request obligatorio, checks de CI que deben pasar, sin force push y, si hace falta, archivo CODEOWNERS para pedir revisión a quien conoce cada parte. Es lo primero que conviene configurar en cualquier repo de equipo.
